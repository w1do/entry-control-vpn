# panel-auth — Delta

## ADDED Requirements

### Requirement: Единственный администратор из .env
Система ДОЛЖНА создавать единственного администратора при первом запуске из переменных `ADMIN` и `PASSWORD`.

#### Scenario: Первый запуск
- **WHEN** БД пуста и заданы `ADMIN` и `PASSWORD`
- **THEN** создаётся пользователь с email из `ADMIN` и хешем пароля argon2id
- **AND** в лог пишется событие `admin_bootstrapped` без пароля

#### Scenario: Слабый bootstrap-пароль
- **WHEN** пароль из `PASSWORD` короче 12 символов
- **THEN** пользователь создаётся, но в лог пишется предупреждение `weak_admin_password` с рекомендацией сменить пароль
- **AND** предупреждение видно на дашборде до смены пароля

#### Scenario: Отсутствуют обязательные переменные
- **WHEN** при старте отсутствует `ADMIN`, `PASSWORD`, `SECRET_KEY` или `ENCRYPTION_KEY`
- **THEN** приложение завершается с понятной ошибкой конфигурации, не поднимая HTTP-сервер

#### Scenario: Повторный запуск
- **WHEN** приложение стартует при непустой БД
- **THEN** существующий администратор не перезаписывается значениями из `.env` (защита от случайной смены пароля деплоем)

### Requirement: Вход по email и паролю
Система ДОЛЖНА аутентифицировать администратора по email и паролю.

#### Scenario: Успешный вход
- **WHEN** администратор отправляет корректные email и пароль
- **THEN** создаётся серверная сессия с opaque-токеном (не JWT), cookie `HttpOnly; Secure; SameSite=Lax` на 7 дней; токен хранится на сервере и может быть отозван
- **AND** сессия ротируется при каждом входе, старые сессии инвалидируются

#### Scenario: Неверные данные
- **WHEN** email или пароль неверны
- **THEN** возвращается 401 с общей формулировкой без указания, что именно неверно
- **AND** попытка заносится в журнал безопасности

### Requirement: Защита API и CSRF
Все маршруты, кроме публичных, ДОЛЖНЫ требовать аутентификацию соответствующего типа: сессию админа (`/api/v1/*`), bearer-токен агента (`/agent/v1/*`), токен метрик (`/metrics`) или токен подписки (`/sub/{token}`). Публично доступны только `/healthz` и `/api/v1/auth/login`.

#### Scenario: Неаутентифицированный запрос
- **WHEN** запрос к `/api/v1/*` приходит без валидной сессии
- **THEN** возвращается 401 без выполнения действия

#### Scenario: Публичная подписка
- **WHEN** VLESS-клиент запрашивает `/sub/{token}`
- **THEN** отдаётся профиль только для валидного неугадываемого токена, ответ не содержит админских данных
- **AND** запросы к `/sub/*` ограничены по rate limit и логируются без токена

#### Scenario: CSRF
- **WHEN** выполняется мутирующий запрос (`POST/PUT/PATCH/DELETE`)
- **THEN** проверяется заголовок `X-CSRF-Token`, соответствующий cookie сессии
- **AND** запрос без токена отклоняется с 403

### Requirement: Ограничение попыток входа
Система ДОЛЖНА ограничивать перебор пароля.

#### Scenario: Перебор
- **WHEN** с одного IP совершено 5 неудачных попыток за 5 минут
- **THEN** попытки блокируются на 15 минут с ответом 429
- **AND** события фиксируются в журнале безопасности

### Requirement: Смена пароля из панели
Система ДОЛЖНА позволять администратору сменить пароль после входа.

#### Scenario: Смена пароля
- **WHEN** администратор указывает текущий и новый пароль (не короче 12 символов)
- **THEN** хеш обновляется, все прочие сессии инвалидируются
- **AND** `.env` не меняется; при последующем деплое пароль остаётся новым

### Requirement: Журнал безопасности
Система ДОЛЖНА вести журнал входов и действий администратора.

#### Scenario: Запись событий
- **WHEN** происходят вход, выход, смена пароля, изменение маршрутизации или удаление сервера
- **THEN** в журнал пишутся событие, время (UTC), IP, user-agent и объект действия
- **AND** пароли, токены и SSH-ключи в журнал не попадают
