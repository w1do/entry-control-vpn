# observability — Delta

## ADDED Requirements

### Requirement: Приём метрик с узлов
Система ДОЛЖНА принимать батчи метрик от агентов и складывать их в хранилище временных рядов.

#### Scenario: Приём батча
- **WHEN** агент отправляет `POST /agent/v1/metrics` с интервалом 15 секунд
- **THEN** панель валидирует токен и сохраняет дельты: байты up/down по узлу и по клиентам, число принятых и заблокированных соединений, онлайн-клиентов и их IP, число ошибок по категориям, состояние процессов и ревизию конфигурации
- **AND** метки времени нормализуются в UTC

### Requirement: Корректность счётчиков
Система ДОЛЖНА считать трафик только по дельтам кумулятивных счётчиков.

#### Scenario: Дельта-базлайн
- **WHEN** агент собирает счётчики `user>>>…` и `inbound/outbound`
- **THEN** трафик вычисляется как разница с предыдущим срезом; рестарт ядра или уменьшение счётчика не даёт отрицательных значений и не теряет данные
- **AND** квоты клиентов считаются только по `user>>>`-счётчикам, outbound-счётчики — для диагностики
- **AND** `int64`-значения не теряют точность (строки/BigInt), `reset=true` не используется, коллектор на узел — один

### Requirement: Агрегация и ретенция
Система ДОЛЖНА агрегировать метрики и хранить их с заданной ретенцией.

#### Scenario: Политика хранения
- **WHEN** данные старше указанного окна
- **THEN** сырые 15-секундные точки сворачиваются в 1-минутные (хранятся 24 ч), 1-минутные — в 5-минутные (30 суток), 5-минутные — в часовые (365 суток)
- **AND** фоновый job выполняет свёртку и удаление устаревших данных

### Requirement: Дашборд
Система ДОЛЖНА показывать сводку состояния и трафика.

#### Scenario: Открытие дашборда
- **WHEN** админ открывает Dashboard
- **THEN** отображаются карточки: узлы онлайн/всего, трафик за сегодня, активные соединения, ошибки за час, доступность маршрутизации
- **AND** график трафика за 24 ч с разбивкой по узлам и список последних инцидентов

### Requirement: Статистика подключений
Система ДОЛЖНА показывать количество подключений и онлайн-клиентов.

#### Scenario: Подключения
- **WHEN** админ смотрит метрики узла
- **THEN** отображаются: принятые соединения в минуту (rate из access-лога), онлайн-клиенты и их IP (`GetUsersStats`), распределение по клиентам
- **AND** источник данных и метод расчёта задокументированы в UI (tooltip)

### Requirement: Статистика ошибок
Система ДОЛЖНА учитывать ошибки маршрутизации и сбои.

#### Scenario: Ошибки
- **WHEN** в логах Xray появляются `rejected` или `[Error]`-события либо health-check выходов падает
- **THEN** панель агрегирует ошибки по категориям (routing_blocked, protocol_rejected, xray_error, health_failed, apply_failed) и показывает их на графике и в списке инцидентов
- **AND** `accepted ... [vless-in -> block]` считается блокировкой маршрутизации, а не ошибкой; доступен топ-10 доменов по блокировкам за период

### Requirement: Аптайм узлов и сервиса
Система ДОЛЖНА рассчитывать доступность узлов и отображать простои.

#### Scenario: Расчёт uptime
- **WHEN** админ открывает узел за период (24 ч / 7 д / 30 д)
- **THEN** показывается uptime % по heartbeat-окнам и uptime процесса Xray из `GetSysStats`, список интервалов простоя с длительностью и причинами (offline/apply_failed/agent_restart)
- **AND** для сервиса в целом показывается доступность API панели

### Requirement: Задержка данных и часовые пояса
Система ДОЛЖНА обеспечивать свежесть данных и корректное отображение времени.

#### Scenario: Свежесть
- **WHEN** метрики собраны на узле
- **THEN** они появляются в панели не позднее чем через 60 секунд
- **AND** время хранится в UTC, отображается в часовом поясе браузера

### Requirement: Инциденты и уведомления в панели
Система ДОЛЖНА создавать инциденты по ключевым событиям и позволять их подтверждать.

#### Scenario: Инцидент «узел offline»
- **WHEN** узел перешёл в offline
- **THEN** создаётся инцидент с severity `critical`, он виден на дашборде и в колокольчике
- **AND** админ может подтвердить (ack) инцидент; при восстановлении узел помечается resolved

#### Scenario: Инцидент «выход недоступен»
- **WHEN** выход помечен down и он входит в allowlist хотя бы одного site rule
- **THEN** создаётся инцидент `warning` с указанием затронутых сайтов

### Requirement: Экспорт метрик
Система ДОЛЖНА отдавать метрики через API для внешнего мониторинга.

#### Scenario: Prometheus-эндпоинт
- **WHEN** внешняя система опрашивает `GET /metrics` с токеном
- **THEN** отдаются метрики: node_up, xray_up, traffic_bytes_total, connections_active, errors_total, uptime_seconds
- **AND** эндпоинт защищён отдельным `METRICS_TOKEN`
