# deployment — Delta

## ADDED Requirements

### Requirement: Развёртывание в Dokploy
Система ДОЛЖНА разворачиваться в Dokploy одной compose-конфигурацией.

#### Scenario: Compose-сервис
- **WHEN** администратор создаёт в Dokploy Compose-сервис из репозитория
- **THEN** поднимаются контейнеры `app` (backend + собранный frontend) и, при необходимости, `db` (Postgres)
- **AND** назначенный домен обслуживается через Traefik с автоматическим TLS

#### Scenario: Публикация порта
- **WHEN** контейнер `app` запущен
- **THEN** наружу открыт только HTTP-порт приложения (через Traefik), БД наружу не публикуется, агентские эндпоинты доступны по HTTPS

#### Scenario: Переменные, домены и сеть в Dokploy
- **WHEN** сервис разворачивается или обновляется в Dokploy
- **THEN** переменные передаются через `env_file`/`${VAR}` рядом с compose (Dokploy не инжектит `.env` автоматически), домены задаются в compose-сервисе и применяются только после redeploy
- **AND** наружу открыты только 80/443, внутренние сервисы — во внутренней сети (`dokploy-network`/internal), данные — на named volume, healthcheck обязателен

### Requirement: Контракт переменных окружения
Система ДОЛЖНА документировать и валидировать переменные окружения.

#### Scenario: Обязательные переменные
- **WHEN** приложение стартует
- **THEN** проверяются `ADMIN`, `PASSWORD`, `SECRET_KEY`, `ENCRYPTION_KEY`, `PUBLIC_BASE_URL`, `DATABASE_URL` (или значение по умолчанию)
- **AND** пример всех переменных с комментариями хранится в `.env.example`

#### Scenario: Секреты
- **WHEN** конфигурация выводится в лог или диагностику
- **THEN** значения `PASSWORD`, `SECRET_KEY`, `ENCRYPTION_KEY` и SSH-ключей маскируются

### Requirement: Секреты не попадают в репозиторий
Репозиторий НЕ ДОЛЖЕН содержать реальных значений `ADMIN`, `PASSWORD`, `SECRET_KEY`, `ENCRYPTION_KEY`, `METRICS_TOKEN` и SSH-секретов.

#### Scenario: Проверка перед сборкой
- **WHEN** собирается образ или запускается CI
- **THEN** выполняется secret-scan (gitleaks/регулярные выражения) по рабочему дереву, и при находке реального пароля/ключа сборка падает
- **AND** `.env` находится в `.gitignore`, а `.env.example` содержит только плейсхолдеры и команды генерации ключей

#### Scenario: Ротация скомпрометированного секрета
- **WHEN** секрет попал в коммит, публикацию или лог
- **THEN** выполняется документированная процедура: смена пароля в Dokploy, перегенерация `SECRET_KEY` (инвалидирует сессии) и `ENCRYPTION_KEY` (требует перешифрования сохранённых секретов), проверка истории git
- **AND** инцидент фиксируется в журнале событий

### Requirement: Миграции и health-check
Система ДОЛЖНА автоматически применять миграции и предоставлять health-check.

#### Scenario: Старт контейнера
- **WHEN** контейнер `app` стартует
- **THEN** выполняются миграции Alembic, затем запускается сервер
- **AND** `GET /healthz` возвращает 200 `{"status":"ok","db":"ok","version":"..."}`

#### Scenario: Неудачная миграция
- **WHEN** миграция завершается ошибкой
- **THEN** контейнер не переходит в healthy, в логах — причина, предыдущая версия может быть восстановлена откатом образа

### Requirement: Хранение состояния
Система ДОЛЖНА сохранять данные между перезапусками и обновлениями.

#### Scenario: Том SQLite
- **WHEN** используется SQLite (по умолчанию)
- **THEN** файл БД лежит на постоянном томе Dokploy (`/data/app.db`)
- **AND** перезапуск/обновление контейнера не теряет серверы, правила и клиентов

#### Scenario: Резервное копирование
- **WHEN** админ запускает экспорт
- **THEN** доступны скачивание резервной копии БД и инструкция восстановления
- **AND** секреты в бэкапе зашифрованы тем же `ENCRYPTION_KEY`

### Requirement: Раздача артефактов агента и Xray
Система ДОЛЖНА отдавать узлам проверенные артефакты.

#### Scenario: Скачивание агента
- **WHEN** узел провижинится
- **THEN** панель передаёт `vpn-agent` и `xray` по SSH (SFTP) либо отдаёт по `GET /agent/v1/artifacts/<name>` с SHA-256
- **AND** версия артефактов фиксируется и отображается в UI

### Requirement: Обновление версии
Система ДОЛЖНА обновляться без потери данных и с обратной совместимостью миграций.

#### Scenario: Обновление образа
- **WHEN** в Dokploy разворачивается новая версия
- **THEN** миграции применяются вперёд, старые данные читаются, контейнер проходит health-check
- **AND** при провале health-check Dokploy откатывает на предыдущий образ, данные не теряются

### Requirement: Логи и наблюдаемость
Система ДОЛЖНА писать структурированные логи в stdout.

#### Scenario: Формат логов
- **WHEN** приложение обрабатывает запрос или job
- **THEN** в stdout пишется JSON-строка с `ts`, `level`, `request_id`/`job_id`, `event` и длительностью
- **AND** секреты и тела SSH-команд с паролями не логируются

### Requirement: Ресурсные лимиты
Система ДОЛЖНА оставаться лёгкой по ресурсам.

#### Scenario: Базовый профиль
- **WHEN** сервис работает без активного провижининга
- **THEN** потребление памяти контейнером `app` не превышает 256 МБ, CPU в покое — менее 5%
- **AND** в `docker-compose` заданы `healthcheck` и лимиты ресурсов
