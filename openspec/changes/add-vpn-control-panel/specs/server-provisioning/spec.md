# server-provisioning — Delta

## ADDED Requirements

### Requirement: Добавление сервера через SSH
Система ДОЛЖНА принимать параметры SSH-подключения (host, port, user, пароль или приватный ключ), проверять их и создавать запись сервера.

#### Scenario: Успешная проверка SSH
- **WHEN** админ отправляет форму добавления сервера с корректными host, port, user и ключом/паролем
- **THEN** система подключается по SSH, определяет ОС, версию ядра и архитектуру, проверяет наличие sudo и свободных портов
- **AND** возвращает предпросмотр (ОС, архитектура, свободен ли 443/tcp, есть ли уже установка VPN) до запуска провижининга

#### Scenario: Ошибка подключения
- **WHEN** SSH-аутентификация или сеть недоступны
- **THEN** система возвращает код ошибки (host_unreachable, auth_failed, sudo_unavailable) с человекочитаемым пояснением
- **AND** запись сервера не создаётся

### Requirement: Провижининг узла одной операцией
Система ДОЛЖНА разворачивать на сервере всё необходимое: `~/config/vpn`, Xray фиксированной версии, `vpn-agent`, юниты systemd, начальную конфигурацию и правила firewall — без ручных шагов.

#### Scenario: Провижининг чистого VPS
- **WHEN** админ запускает провижининг для прошедшего preflight сервера
- **THEN** система создаёт `~/config/vpn/{bin,etc,log,state}`, устанавливает Xray и vpn-agent, создаёт юниты `xray.service` и `vpn-agent.service`, включает автозапуск
- **AND** запускает сервисы, проверяет `is-active` и локальную проверку конфигурации
- **AND** переводит сервер в статус `online`

#### Scenario: Поток прогресса
- **WHEN** провижининг выполняется
- **THEN** UI получает шаги через SSE (каталоги, загрузка Xray, установка агента, firewall, запуск, регистрация)
- **AND** при провале шага статус `failed` с указанием шага и stderr

#### Scenario: Идемпотентный повтор
- **WHEN** провижининг повторно запускается на частично настроенном сервере
- **THEN** существующие компоненты не дублируются, отсутствующие доустанавливаются, итог — рабочий узел

### Requirement: Регистрация узла в панели
Система ДОЛЖНА выпускать узлу уникальный токен агента и считать узел подключённым после первого heartbeat с корректным токеном.

#### Scenario: Узел онлайн
- **WHEN** агент зарегистрировался по HTTPS и прислал heartbeat
- **THEN** сервер получает статус `online`, отображаются версии агента и Xray, uptime и ревизия конфигурации
- **AND** QR/ссылка показываются только для узлов с ролью `entry`

### Requirement: Роли узла
Система ДОЛЖНА поддерживать роли `entry`, `exit`, `both`, назначаемые при добавлении и изменении сервера.

#### Scenario: Назначение роли exit
- **WHEN** админ присваивает серверу роль exit и регион (например, SG)
- **THEN** узел публикуется как доступный выход и появляется в выборе выходов для сайтов
- **AND** конфигурации всех entry-узлов перегенерируются с outbound на новый узел

#### Scenario: Назначение роли entry
- **WHEN** админ присваивает серверу роль entry
- **THEN** узел получает inbound VLESS+REALITY и доступен для клиентских ссылок

### Requirement: Статусы, heartbeat и degraded
Система ДОЛЖНА отслеживать живость узлов и помечать их `offline`/`degraded`.

#### Scenario: Узел пропал
- **WHEN** heartbeat отсутствует дольше 90 секунд
- **THEN** сервер помечается `offline`, дашборд показывает инцидент, выходы этого узла считаются недоступными

#### Scenario: Дрейф конфигурации
- **WHEN** агент обнаружил, что фактический конфиг Xray не совпадает с утверждённой ревизией
- **THEN** сервер помечается `degraded`, панель предлагает переприменение конфигурации

### Requirement: Удаление сервера с полной очисткой
Система ДОЛЖНА при удалении сервера остановить и отключить юниты, удалить `~/config/vpn`, снять правила firewall, отозвать токен и удалить запись.

#### Scenario: Удаление доступного сервера
- **WHEN** админ подтверждает удаление (ввод имени сервера) и SSH доступен
- **THEN** выполняется uninstall: disable+stop `vpn-agent` и `xray`, удаление `~/config/vpn`, снятие правил firewall и юнитов
- **AND** после проверки (каталог отсутствует, юниты не загружены) запись удаляется из БД

#### Scenario: Удаление недоступного сервера
- **WHEN** SSH недоступен во время удаления
- **THEN** job завершается ошибкой, запись остаётся в статусе `delete_pending` с возможностью повтора
- **AND** доступно принудительное удаление записи с явным предупреждением, что узел может остаться настроенным

### Requirement: Список и карточка сервера
Система ДОЛЖНА показывать список серверов и карточку с деталями и действиями.

#### Scenario: Просмотр списка
- **WHEN** админ открывает вкладку Servers
- **THEN** отображаются имя, роль, регион, статус, версии, последний heartbeat, трафик за 24 ч и uptime
- **AND** доступны действия: переприменить конфиг, перезапустить сервисы, переустановить, удалить

### Requirement: Безопасность SSH-кредов
Система ДОЛЖНА хранить SSH-секреты зашифрованными и не возвращать их через API.

#### Scenario: Креды не утекают
- **WHEN** UI запрашивает карточку сервера
- **THEN** ответ содержит только тип аутентификации и отпечаток ключа, без пароля и приватного ключа
- **AND** секреты расшифровываются только на время SSH-операции и не попадают в логи
