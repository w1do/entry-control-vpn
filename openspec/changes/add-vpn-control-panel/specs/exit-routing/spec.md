# exit-routing — Delta

## ADDED Requirements

### Requirement: Управление выходами
Система ДОЛЖНА вести реестр выходов (exit-узлов), доступных для проксирования.

#### Scenario: Выход доступен
- **WHEN** сервер имеет роль exit или both и прошёл провижининг
- **THEN** он появляется в реестре выходов с меткой региона (например, «Сингапур»), статусом здоровья и счётчиком использования
- **AND** адмin может временно отключить выход, не удаляя сервер

#### Scenario: Выход отключён
- **WHEN** админ отключает выход
- **THEN** конфигурации entry-узлов перегенерируются без него, а сайты, у которых он был единственным разрешённым, начинают блокироваться (fail-closed)

### Requirement: Внешние выходы через резидентские прокси
Система ДОЛЖНА поддерживать выходы типа «внешний прокси» (HTTP/HTTPS CONNECT или SOCKS5) наравне с exit-узлами.

#### Scenario: Добавление резидентского выхода
- **WHEN** админ добавляет выход типа `external_proxy` с host, port, логином/паролем, регионом и ожидаемым exit-IP
- **THEN** система сохраняет креды зашифрованными, компилирует для entry-узла outbound на этот прокси и делает выход доступным в правилах сайтов
- **AND** можно задать sticky-сессию (параметр логина провайдера) и месячный бюджет трафика

#### Scenario: Проверка фактического exit-IP
- **WHEN** выполняется health-check внешнего выхода
- **THEN** система делает контрольный запрос через цепочку и сравнивает фактический IP и страну с ожидаемыми
- **AND** при несовпадении, стране `RU` или недоступности выход помечается `down`, а сайты с этим выходом блокируются (fail-closed)

#### Scenario: Учёт трафика и бюджет
- **WHEN** через внешний прокси идёт трафик
- **THEN** панель считает байты по каждому внешнему выходу и показывает расход относительно бюджета провайдера
- **AND** при приближении к лимиту создаётся инцидент `warning`, при исчерпании — выход отключается

### Requirement: Профиль маршрутизации с обязательным выходом по умолчанию
Система ДОЛЖНА иметь один активный профиль маршрутизации, в котором выход по умолчанию задан явно и не может быть «не задан» для включённого профиля.

#### Scenario: Профиль не настроен
- **WHEN** активный профиль не имеет выхода по умолчанию или ни одного health-выхода
- **THEN** система запрещает включение маршрутизации, все entry-узлы работают в режиме `block all`
- **AND** UI показывает баннер «Проксирование не настроено» с переходом в настройку

#### Scenario: Выход по умолчанию задан
- **WHEN** админ выбирает выход по умолчанию и профиль валиден
- **THEN** система компилирует конфигурацию: зарубежный трафик без явных правил идёт через этот выход

### Requirement: Российские сайты не проксируются
Система НЕ ДОЛЖНА проксировать российские домены и IP: они обслуживаются напрямую и никогда не попадают на exit-выходы.

#### Scenario: RU-домен в умном профиле (основной режим)
- **WHEN** клиент использует клиентский профиль с RU-bypass
- **THEN** запросы к `geosite:category-ru` и `geoip:ru` уходят напрямую с устройства клиента (российский IP) и не покидают устройство в туннель
- **AND** в UI режим подписан как «Российские сайты — как есть (напрямую)»

#### Scenario: RU-домен при полном туннеле (fallback)
- **WHEN** клиент подключён по чистому `vless://` без клиентских правил
- **THEN** entry-узел направляет RU-домены/IP в `direct` и не отправляет их ни на один выход
- **AND** UI явно поясняет, что в этом режиме RU-трафик проходит через entry-IP, а не напрямую с устройства

#### Scenario: Попытка обойти
- **WHEN** API получает попытку добавить site rule, перекрывающий RU-диапазон
- **THEN** запрос отклоняется с ошибкой `ru_direct_locked`

### Requirement: Правила по сайтам с allowlist выходов
Система ДОЛЖНА позволять задавать для домена/набора доменов явный упорядоченный список разрешённых выходов.

#### Scenario: Anthropic только на выбранных выходах
- **WHEN** админ в карточке сайта Anthropic выбирает выходы SG-1 и US-1 (в этом порядке)
- **THEN** запросы к `anthropic.com`, `claude.ai`, `api.anthropic.com` и связанным доменам идут только через SG-1, при его недоступности — через US-1
- **AND** при недоступности обоих соединение блокируется; запрос НЕ уходит ни на выход по умолчанию, ни напрямую
- **AND** попытка добавить в тот же список неразрешённый выход отклоняется валидацией

#### Scenario: Сайт без явного правила
- **WHEN** домен не совпал ни с одним site rule и не является RU
- **THEN** он идёт через выход по умолчанию

### Requirement: Fail-closed маршрутизация
Система НЕ ДОЛЖНА допускать деградацию маршрута «через разрешённый выход → через любой доступный → напрямую».

#### Scenario: Все разрешённые выходы недоступны
- **WHEN** health-check показывает, что все выходы из allowlist сайта недоступны
- **THEN** соединения к этому сайту отклоняются (`block`), в статистике фиксируется `rejected`, в панели появляется инцидент
- **AND** после восстановления хотя бы одного выхода маршрут возвращается автоматически без ручных действий

#### Scenario: Отсутствие final-маршрута в direct
- **WHEN** компилятор строит конфигурацию
- **THEN** финальное правило — `block`/`reject`, первый outbound в конфиге — `blackhole`, приватные IP и metadata (`169.254.169.254`) блокируются первым правилом, а `direct` используется только для RU-правил и служебного трафика
- **AND** golden-тест проверяет, что в скомпилированном конфиге нет возможности «утечки» в direct

### Requirement: Компиляция и применение профиля
Система ДОЛЖНА компилировать профиль в детерминированный конфиг Xray и применять его на всех entry-узлах с ревизией и откатом.

#### Scenario: Применение изменений
- **WHEN** админ сохраняет изменения маршрутизации
- **THEN** создаётся новая ревизия, конфиг валидируется (`xray -test`) на каждом entry-узле, применяется атомарно, проверяется health
- **AND** при провале хотя бы одного узла применяется откат к предыдущей ревизии на всех узлах, UI показывает ошибку

#### Scenario: Компиляция детерминирована
- **WHEN** одно и то же состояние БД компилируется дважды
- **THEN** получается байт-идентичный JSON конфигурации (ключи отсортированы, порядок правил фиксирован)

### Requirement: Проверка эффективного маршрута
Система ДОЛЖНА показывать, куда уйдёт запрос для заданного домена, до применения.

#### Scenario: Проверить домен
- **WHEN** админ вводит домен в «Проверить маршрут»
- **THEN** система возвращает: совпавшее правило, тип (RU-direct / site rule / default / block), выбранный выход или `block`
- **AND** проверка использует ту же функцию сопоставления, что и компилятор, с примером скомпилированного правила

### Requirement: DNS-политика
Entry-узлы ДОЛЖНЫ резолвить домены через заданный DoH-резолвер через выход, не используя системный резолвер узла.

#### Scenario: Резолвинг
- **WHEN** entry-узел разрешает имя для маршрутизации или для клиента
- **THEN** запрос идёт на DoH (например `https://1.1.1.1/dns-query`) через выход по умолчанию
- **AND** системные DNS-настройки узла и российские резолверы не используются

### Requirement: Здоровье выходов
Система ДОЛЖНА проверять доступность выходов и вести историю их доступности.

#### Scenario: Проверка выхода
- **WHEN** наступает интервал health-check (30 секунд)
- **THEN** панель инициирует проверку через узел (запрос `generate_204` через цепочку) и фиксирует результат, задержку и фактический exit-IP
- **AND** при провале N проверок подряд выход помечается `down` и исключается из балансировки

### Requirement: Пресеты сайтов
Система ДОЛЖНА содержать пресеты популярных сервисов для быстрого добавления правил.

#### Scenario: Добавление пресета Anthropic
- **WHEN** админ нажимает «Добавить Anthropic» и выбирает выходы
- **THEN** создаётся site rule с набором доменов пресета (`anthropic.com`, `claude.ai`, `claude.com`, `console.anthropic.com`, `api.anthropic.com`) и выбранным allowlist
- **AND** пресет можно отредактировать или удалить

### Requirement: Аудит изменений маршрутизации
Система ДОЛЖНА фиксировать историю изменений профиля.

#### Scenario: История
- **WHEN** профиль изменён и применён
- **THEN** в журнале сохраняются кто (единственный админ), время, diff ревизий и результат применения
- **AND** доступен просмотр и сравнение ревизий
