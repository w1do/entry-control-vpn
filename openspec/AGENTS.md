# OpenSpec Instructions

Инструкции для AI-агентов, работающих в этом проекте.

Открывай `openspec/AGENTS.md`, когда запрос:
- упоминает планирование или предложения (proposal, spec, change, plan);
- вводит новые возможности, ломающие изменения, смену архитектуры или крупную работу по производительности/безопасности;
- звучит неоднозначно и нужна авторитетная спецификация до кодирования.

Что здесь описано:
- как читать и создавать change proposals;
- формат спецификаций и конвенции;
- структура проекта и правила работы.

## Структура

```
openspec/
├── project.md              # контекст проекта, стек, соглашения
├── specs/                  # источник правды (capability/spec.md)
├── changes/                # активные изменения
│   ├── <change-id>/
│   │   ├── proposal.md     # зачем и что меняется
│   │   ├── design.md       # архитектурные решения и альтернативы
│   │   ├── tasks.md        # чек-лист реализации
│   │   └── specs/<capability>/spec.md   # дельты требований
│   └── archive/            # завершённые изменения
└── AGENTS.md
```

## Формат требований

```md
## ADDED Requirements

### Requirement: <краткое название>
Система ДОЛЖНА <поведение>.

#### Scenario: <сценарий>
- **WHEN** <условие>
- **THEN** <ожидаемый результат>
```

- Каждое требование — проверяемое поведение, не «намерение».
- Каждое требование имеет минимум один Scenario.
- Дельты: `## ADDED`, `## MODIFIED`, `## REMOVED`, `## RENAMED Requirements`.
- После реализации изменение архивируется: дельты переносятся в `openspec/specs/<capability>/spec.md`.

## Правила работы

1. Сначала прочитать `openspec/project.md` и активный change.
2. Менять поведение — только через change (proposal → design → specs → tasks).
3. Не смешивать несколько изменений в одном change.
4. Задачи в `tasks.md` отмечать по мере выполнения; реализация без спеки не принимается.
5. При конфликте спеки и кода — спека обновляется отдельным change.
